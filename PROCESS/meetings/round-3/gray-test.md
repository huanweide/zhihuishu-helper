## 0. 一句话结论（给完全不懂技术的读者）

这个插件**整体是稳的**——三个新功能在正常使用下不会乱动、不会把网页搞崩、不会偷偷替你答题。但我在边边角角挖出了 **2 个「严重」问题**（其中一个已当场修好）和 **6 个「一般」问题**。

最关键的一条：**如果用户的配置数据在某次意外里被写成了 `null`，旧版代码会让整个助手彻底瘫痪**（页面上一片红，什么功能都不工作）。这是我在开发者的自测里没看到覆盖到的角落，我已经把这一条修掉了，并且回归测试通过。

我还顺手修了第二个真缺陷：**当作业标题写的是「第三章」而不是「第3章」时，章节过滤功能失效**——用户明明设了「只答 1~2 章」，第三章的作业还是会被自动作答。真实站点恰恰常用「第三章」这种中文数字写法。

## 1. 测试做了什么（通俗版）

### 1.1 什么是「灰度测试」

普通测试（灰/白盒的「白盒」）像是**把发动机拆开看每个零件**；灰度测试介于中间——**既模拟真实用户点击操作，又钻进代码里核对每一行逻辑**，专门找开发者自己测的时候没想到的「角落」。

### 1.2 我用什么模拟「真实网页」

我用了一个叫 **jsdom** 的工具（一个在 Node.js 里跑的「假浏览器」）。它能：
- 假装自己是一个真实的网页（有 DOM 元素、有 URL、有 localStorage）；
- 让插件的 16 个源码模块在「假浏览器」里真实运行；
- 把「假浏览器」里的真实结果（哪个按钮被点了、哪条日志打出来了、配置变成什么样了）原样抓出来验证。

**关键细节（保证测试可信）**：加载源码必须用 `vm.runInContext(code, dom.getInternalVMContext())`——这是把代码注入到「假浏览器」里的正确姿势。如果图省事用 `window.eval`，代码会在真实 Node 环境里跑，隔离性就没了，测出来的结果不作数。我的脚本严格用了正确姿势。

## 2. 【严重】问题（会功能失效 / 数据损坏 / 污染全局）

### 严重-1：配置存成字面量 `"null"` 时，整个助手彻底瘫痪（已修复 ✅）

**问题白话**：插件把用户设置（倍速、开关等）存在一个叫 `zhs-helper-config` 的地方。正常情况存的是一段 JSON 文本，比如 `{"speed":1.5,...}`。但如果这段数据因为某种意外变成了字符串 `null`（4 个字母组成的文本，不是「空」，是「写着 null 两个字」），旧代码在读取时会当场抛出一个错误，导致**整个脚本从第一行就崩，所有功能失效**——页面上的面板虽然挂出来了，但每次刷新都报错，主循环每 2 秒往控制台打一条错误。

**我是怎么发现的**（证据）：
1. 我枚举了各种「脏数据」喂给配置读取函数，发现只有 `"null"` 这一个值会打穿防线：

```
null         -> OK(saved={})
""           -> OK(saved={})
"{}"         -> OK(saved={})
"[]"         -> OK(saved=[])
"\"abc\""    -> OK(saved="abc")
"123"        -> OK(saved=123)
"true"       -> OK(saved=true)
"null"       -> THROW: Cannot read properties of null (reading 'configRev')   ← 唯一崩溃值
"undefined"  -> OK(saved={})
"{bad"       -> OK(saved={})
```

2. 定位到崩溃点：`src/00-config.js:114`
```js
if (Number(saved.configRev || 0) < CONFIG_REV) {   // saved 为 null 时这里抛 TypeError
```
**根因**：第 108 行 `saved = JSON.parse(raw)`，当 `raw` 是 `"null"` 时，`JSON.parse("null")` 返回的是真正的 `null`。第 108 行的 `if (raw)` 只检查了「原始字符串是否为空」，**没检查解析出来的结果是不是对象**。于是 `saved` 变成 `null`，第 114 行访问 `saved.configRev` 就崩了。

3. 连整份 bundle（打包后的完整脚本）一起验证：旧版抛 `Cannot read properties of null (reading 'configRev')`，脚本中断。（修复后同一场景不再抛错。）

**修复**（`src/00-config.js`，改动 4 行）：
```js
// 兜底：JSON.parse 可能产出 null / 数字 / 字符串 / 数组等非对象值
// （例如历史脏数据里存了字面量字符串 "null"）。此类值会让下面的
// saved.configRev 抛 TypeError，进而中断整份脚本。统一退化回空对象。
if (!saved || typeof saved !== 'object' || Array.isArray(saved)) saved = {};
```
这段代码的作用：**只要读出来的不是一个正经对象，就一律当「没有配置」处理，用默认值兜底**。这样任何奇怪的数据都打不穿防线了。

**修复后验证**：`test/gray-v060.js` 里两条相关断言变成绿色「回归守卫」，回归测试全绿：
```
✓ 【回归守卫】zhs-helper-config="null" 读配置不再抛 TypeError（原严重缺陷已修）
✓ 【回归守卫】配置为 null 时整份 bundle 不再中断（原严重缺陷已修）
```

> **为什么严重**：油猴脚本里任何一个未捕获异常都可能让整份脚本中断。配置读取是**每个模块启动时都会调用**的最底层函数，它一崩，全盘皆输。这类数据损坏在真实场景中并不罕见（历史版本写入格式变更、同步冲突、手动改错等）。

## 3. 【一般】问题（功能不崩，但行为不对 / 有隐患）

### 一般-1：只开「自动跳课」不开「自动选课」时，跳转意图残留，之后会「诈尸」自动点课（未修，建议修）

**问题白话**：插件有个跨页面的「小纸条」机制（代码里叫 `intent`，跳转意图）。当一门课学完、准备跳回课程中心时，它会在小纸条上写「我是自动跳过来的，回来要记得自动选下一门课」。

但现在有个漏洞：如果用户**只开了「自动跳课」、关了「自动选课」**，插件跳回课程中心后，看到「自动选课」是关的，就直接掉头走了——**根本没去把那张小纸条撕掉**。于是纸条一直留在存储里。

后果：**过一段时间，用户把「自动选课」打开了**，插件一进课程中心，看到那张「老纸条」还在，就以为「这是刚才自动跳过来的，该选课了」，**啪地自动点了一门课**。这违背了产品的核心铁律——「**用户没主动授权时，绝不劫持操作**」。

**证据**（真实输出）：
```
✗ 【缺陷】只开跳课时 intent 未被清理（会残留）
     → intent 残留 = {"courseId":"CID1","courseName":null,"via":"auto-hop","at":1789714203267}
✗ 【缺陷】残留 intent 会让「用户只开了 pick」也触发自动点课（违背「不劫持」铁律）
     → 自动点击 1 次；intent={"courseId":"c2","courseName":"未完成课","via":"auto-hop","at":1789714203602}
```

**根因**（`src/06b-course-hub.js:678`）：
```js
if (!ZHS.config.autoCoursePick) {
  ZHS.Log.debug('[课程中心] 自动选课开关关闭，不动作');
  return;                       // ← 在这里就返回了，下面清理 intent 的代码永远走不到
}
const it = getIntent();         // ← 这行及之后才是「读取并清理 intent」
```
而写小纸条的代码在 `returnToHub()`（`src/06b-course-hub.js:530`）——**写进去，但在「选课关闭」这条路径上没有任何地方把它清除**。

**建议修法**：在 `if (!ZHS.config.autoCoursePick)` 分支里，先调用一次 `clearIntent()` 再 return。即：**只要进到了课程中心，无论选课开不开，都先把过期的自动跳课意图消耗掉**。这样纸条就不会留到下次。

> 我没有直接修这条，因为「何时该清除意图」涉及产品行为取舍（也可能开发者有意保留意图等用户下次手动触发），需要主人拍板。

### 一般-2：作业标题用中文数字「第三章」时，章节过滤失效（已修复 ✅）

**问题白话**：插件有个「只答第几章到第几章」的功能（比如用户设「只答第 1~2 章」）。它需要从作业页标题里读出「这是第几章」。旧代码的正则表达式**只认阿拉伯数字**（`第3章`），**不认中文数字**（`第三章`）。而真实智慧树站点的标题恰恰常用「**第三章**」这种写法。

后果：用户设了「只答 1~2 章」，结果因为读不出章节号，插件**退化为「全部作答」**——第三章的作业也会被自动答掉（越权）。日志里只会含糊地说「未能识别章节」。

**证据**（真实输出）：
```
· detectChapter() 从「第3章 单元测验」识别到  → 3        （阿拉伯数字：能识别 ✓）
✓ 第 3 章不在 1~2 范围内 → 一道不答、不提交              （过滤生效 ✓）
✗ 【缺陷】「第三章」（中文数字）识别不到章节 → 范围过滤失效，退化为全部作答
```
我用一个探针单独验证了正则行为：
```
"第三章 单元测验" -> null     ← 中文数字漏识别
"第3章 单元测验"  -> 3
"第 3 章"         -> 3
```

**根因**（`src/06c-exam.js:111`，修改前）：
```js
const m = String(text || '').match(/第\s*(\d+)\s*[章节单元]/);   // \d+ 只吃阿拉伯数字
```

**修复**（`src/06c-exam.js`，新增中文数字解析，改动约 36 行）：
先加了一个中文数字转阿拉伯数字的小工具 `cnNum()`（处理「三 → 3」「十 → 10」「十五 → 15」等常见写法），再让 `parseChapterFromText()` 在阿拉伯数字匹配失败后，**追加尝试中文数字**：
```js
// 先认阿拉伯数字
let m = t.match(/第\s*(\d+)\s*[章节单元]/);
if (m) { ... }
// 再认中文数字（真实站点标题常写「第三章」）
m = t.match(/第\s*([一二三四五六七八九十零]{1,3})\s*[章节单元]/);
if (m) { const n = cnNum(m[1]); if (Number.isFinite(n) && n > 0) return n; }
```

**修复后验证**：
```
✓ 【回归守卫】「第三章」（中文数字）也能识别到章节（原漏识别缺陷已修）
```

> **为什么算「一般」而不是「严重」**：它不会崩、不会损坏数据，最坏情况是「多答了几道题」，且只在「用户设了章节范围」时才触发。但它确实是个**真实功能失效**，因为在真站点上这种情况很容易命中。

### 一般-3：脏数据 `autoExam="no"`（字符串）绕过开关门禁，自动答题被「偷偷打开」（未修，建议修）

**问题白话**：自动答题这个功能**默认是关的**（安全承诺：「守株待兔」，用户不主动开就绝不动手）。

但如果配置里 `autoExam` 这个值不是 `false`，而是字符串 `"no"`（比如被人工改过、或旧版本写入了字符串），代码判断「开关是否打开」时用的是**真值判断**（非空字符串一律算「真」），而不是严格判断「是不是布尔值 true」。结果：`"no"` 被当成「开」，**门禁失效，插件开始自动答题**——用户以为关着，实际在动。

**证据**（真实输出）：
```
✗ 【缺陷】autoExam="no"（字符串）被当真值 → 开关门禁失效，用户以为关了实际是开
     → autoExam="no" → 门禁 !cfg.autoExam = false；源码 06c-exam.js:515 / 710 用的是真值判断，不是 === true
✗ 【缺陷】autoExam="yes" 时考试模块真的会开始作答（字符串绕过门禁的实际后果）
     → 是否自动勾选 = true（证明脏数据能让守株待兔模块动手）
```
源码核对（`src/06c-exam.js`）：
```js
541:      if (!manual && !cfg.autoExam) return;    // "no" 是真值 → 不 return → 继续作答
736:        if (!cfg.autoExam) {                    // 同上
```

**建议修法**：把 `!cfg.autoExam` 改为 `cfg.autoExam !== true`（严格判断），并可在配置读取时把非布尔值强转为布尔。同类问题还波及 `autoCourseHop="false"`（也在「吹毛求疵」里列了）。

> 理论上，只要配置全程由插件自己读写，不会出现字符串；但历史脏数据 + 面板/GM 直写都可能造成。作为「默认关闭」的安全功能，门禁建议用严格判断。

### 一般-4：重复注入整份 bundle 会抛 `Identifier '__ZHS_VERSION__' has already been declared`（未修，建议修）

**问题白话**：油猴脚本在某些场景（SPA 应用、多个匹配域名各注入一次、或用户手动重装）会**被加载两次**。旧脚本第二次加载时会直接抛一个「标识符已声明」的语法错误。

**证据**（真实输出）：
```
✗ 【问题】重复注入整份 bundle 会抛 "Identifier __ZHS_VERSION__ has already been declared"
     → 抛错：Identifier '__ZHS_VERSION__' has already been declared
```

**根因**（`build.js:45`）：构建脚本在**脚本最外层**注入了一个常量声明：
```js
let body = `\n/* ===== 构建注入 ===== */\nconst __ZHS_VERSION__ = ${JSON.stringify(VER)};\n`;
```
`const` 在同一作用域重复声明是**语法错误**，会在**整个文件第一行**就报错、直接终止。

**好处**：它意外地拦住了「重复挂载」（第二次不会叠加），所以有正面副作用。
**隐患**：如果第一次注入因为某种页面原因只加载了一部分模块，第二次将**永远无法补装**（因为 SyntaxError 在最前面，还没轮到补装就崩了）。

**建议修法**：把这个 `const` 移进一个 IIFE 里，或改成 `var __ZHS_VERSION__ = ...` 并加 `if (typeof __ZHS_VERSION__ === 'undefined')` 守卫。

### 一般-5：只有 `00-config` 有重入守卫，其余 15 个模块重复加载会叠加定时器（未修，建议修）

**问题白话**：脚本里有几个「定时器」（每隔 1.5 秒刷新面板、每隔 3 秒检查作业页等）。如果脚本被加载两次，**面板刷新定时器会变成 2 个**，作业检查定时器也叠加，造成重复动作和资源浪费。

**证据**（真实输出）：
```
✗ 【缺陷】00-config 以外的 15 个模块没有重入守卫，重复加载会叠加定时器
     → 第1轮 1500ms 定时器=1，第2轮=2（面板刷新定时器翻倍；其它模块的 IIFE 会重复执行，
       如 06b 的 setTimeout(onPageReady) 也会叠一份）
```
只有 `00-config.js` 做了防重入（它检查版本号，已加载过就 return），其它模块都是「裸 IIFE」，每次执行都重新挂定时器。

**建议修法**：给每个模块统一加一个 `if (window.__ZHS_HELPER__ && ZHS.xxx) return;` 的守卫，或统一由主入口做单例控制。

### 一般-6：`examChapter*` 章节范围没有做数值夹逼（未修，建议修）

**问题白话**：用户在面板上一般是拖着数字框填的，会走「取整」逻辑。但如果有人**直接调 API 或改存储**写入负数，插件不会拦。

**证据**（真实输出）：
```
· 【缺陷】setConfig API 不夹逼 examChapter*（面板走 floor，API/GM 直写不设防）
     → setConfig({examChapterFrom:-5}) → -5；对比 speed 有硬夹逼（00-config.js:125）
```
对比：`speed`（倍速）在 `src/00-config.js:125` 有硬夹逼 `Math.min(Math.max(...), 0.5), 1.8)`，而 `examChapterFrom/To` 没有任何夹逼。

> 影响很小（面板路径本身会 floor），列出来是为了「对称性」——同类配置项建议都做一次校验。

## 4. 【吹毛求疵】问题（不影响使用，但值得知道）

| # | 问题 | 证据 / 说明 |
