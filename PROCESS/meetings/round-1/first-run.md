## 二、逐条发现

### [UX-FR-1] 第一次打开面板：没有任何新手引导
**证据**
- `src/06-panel.js:107-189` `_html()`：默认落在「状态」页，页面只有 9 行 `kv` 数据（运行状态/页面版本/当前课时/…），**没有一个字告诉用户下一步做什么**。
- `src/06-panel.js:183-188` 底部按钮排布为 `启动 / 停止 / 下一节 / 答题`，四个按钮视觉权重几乎一致，只有「启动」带 `.pri` 蓝色高亮。
- `src/06-panel.js:112-114` 头部只有版本号 `智慧树助手 v0.2.1` 和一个 `—` 折叠按钮，**没有帮助按钮、没有文档链接、没有首次使用 banner**。
- 全文件搜索 `title=` 只有两处：`src/06-panel.js:109` 圆钮的 `title="智慧树助手"`、`src/06-panel.js:113` 的 `title="收起"`。所有开关 label（`06-panel.js:138-180`）均无 tooltip。

**小白感知**
打开就看见一块 320px 的白面板，上面 4 个按钮、状态里写着「未识别」「—」。我心里的问题是：**「我现在要按什么？要不要按？」** 「页面版本：智慧版共享课」这类字段对大学生毫无意义，而真正致命的信息（答题功能没开、没配 Key）一条都没出现在这一页。用户很可能看完状态页就去点「启动」，然后发现「好像已经在跑了 / 好像没反应」。

**建议**
1. 首次挂载时（GM 存储里没有 `zhs-helper-onboarded` 标记）在面板顶部插一条**可关闭的引导条**，文案：「① 已经在自动播放了 ② 想连弹题自动答？去『设置』填模型 Key ③ 卡住看『日志』」，并给「知道了」按钮把标记落盘（用现有 `ZHS.setConfig` 持久化即可）。
2. 「状态」页加一行「下一步建议」，由运行时状态动态生成（未配 Key → 「去设置填 Key」；未启动 → 「点启动」；运行中 → 「挂着就行，别最小化窗口」）。
3. 底部四个按钮加 `title`（原生 tooltip 在 Shadow DOM 内同样生效），成本极低。

### [UX-FR-2] 脚本已经自动启动，但「启动」按钮毫不知情
**证据**
- `src/07-main.js:48` 初始化流程最后一步无条件调用 `ZHS.Scheduler.start()`——也就是说**用户什么都不点，脚本已经在跑**。
- `src/05-scheduler.js:28-36` `start()` 第一行是 `if (this._timer) return;`——**已经在运行的第二次调用会直接 return，不打日志、不弹提示**。
- `src/06-panel.js:335` `$('.btn-start').onclick = () => ZHS.Scheduler.start();`——按钮点击后不产生任何自己能看到的变化。
- `src/06-panel.js:184` 「启动」按钮文案与 `.pri` 样式写死，不随 `ZHS.state.running` 变化。

**小白感知**
我点了「启动」。**屏幕上什么都没发生**（日志页我还没打开）。我会认为「按钮坏了 / 脚本没生效」，然后反复点击，甚至重装脚本。反过来说，我没点「启动」它也在自动播放，一旦我没看说明，会误以为「这软件自己动了」而不敢关。

**建议**
1. 「启动 / 停止」改成**同一个按钮的状态切换**：运行中显示「暂停中…点此停止」或直接把 `.pri` 高亮移给「停止」，让用户一眼看出当前状态。
2. `Scheduler.start()` 在 `this._timer` 已存在时加一行 `ZHS.panel.alert('已经在运行了', 'info')`，给点击反馈。
3. 状态页「运行状态」字段旁边加个绿点/灰点，比纯文字「运行中」更快认出（现状 `06-panel.js:356` 只有文字）。

### [UX-FR-3] 【最严重】没配 Key、题库也不通 → 弹题被**随机乱选**，全程无声
**证据**
- `src/00-config.js:29` `autoAnswer: false`（默认关）
- `src/00-config.js:30` `answerMode: 'both'`
- `src/00-config.js:31` `bankUrl: 'http://localhost:8060'`、`src/00-config.js:32` `bankEnabled: true`（绝大多数学生电脑**没有本地题库**）
- `src/00-config.js:35` `llmKey: ''`（默认空）
- `src/09-bank.js:127-133` 题库请求 `timeout: 12000`，连不上时 `src/09-bank.js:135-137` 只打 `Log.debug('题库无响应（status=' + res.status + '）')`
- `src/11-solver.js:70` LLM 分支的前置条件是 `cfg.llmKey` 非空 → 无 Key 时**整段跳过**
- `src/11-solver.js:82-88` 兜底：
  ```js
  if (!result && options.length) {
    const idx = Math.floor(Math.random() * options.length);
    ...
    ZHS.Log.warn('无可用通道，随机选择 ' + letter);
  }
  ```
- 这条 `warn` 只进日志页，**没有任何 `panel.alert`**。
- 日志会显示「已作答：B（来源 random）」（`src/13-answerer.js:153`），但用户必须在 8 秒内正好翻到日志页才看得见。

**小白感知**
我照着说明打开「自动答题」，填了什么都说可以跑。结果每一道弹题都被**瞎蒙**，正确率约 25%，而且**平台端的答题记录会被写坏**（很多课程允许重答次数有限）。我事后完全不会知道发生了什么，只会觉得「这脚本答题不准」。这是一个会**实质损害用户成绩**的默认行为。

**建议**
1. **删掉随机兜底，或改成「不作答 + 明确提示」**。宁可让用户手动答，也不要替他蒙：`ZHS.panel.alert('没有可用答题通道（未配 Key 且题库不通），已跳过本题', 'error')`。
2. 打开「自动答题」开关时（`06-panel.js:217-225`）做一次**通道健康检查**：Key 为空 → 提示「已开启答题但未配 API Key，弹题将不会作答」；题库 `ping()` 失败 → 提示「题库地址连不上，只有 LLM 可用」。
3. 状态页增加「答题通道」一行实时健康状态（绿/红），而不是只在结束总结里才出现（现状只有 `05-scheduler.js:289` 的总结报告里有）。

### [UX-FR-8] 答题开关三重冗余：模式下拉 + 题库通道 + LLM 通道
**证据**
- `src/11-solver.js:57` 题库生效条件：`(mode === 'bank' || mode === 'both') && cfg.bankEnabled`
- `src/11-solver.js:70` LLM 生效条件：`(mode === 'llm' || mode === 'both') && cfg.llmEnabled && cfg.llmKey`
- 于是「答题模式=仅题库」时，`LLM 通道` 开关无论开闭都无效；反之亦然。两个开关和下拉框**语义交叉**。
- 而且三者分别在 `06-panel.js:148`、`06-panel.js:149`、`06-panel.js:150-156` 三处，用户很容易配出「我明明开了 LLM 通道却不用 LLM」的矛盾组合。

**小白感知**
「我两个通道都开了、模式也选了双通道，怎么还是不答题？」——因为真正卡住的是没 Key（`11-solver.js:70` 的 `cfg.llmKey`），但界面上看不出哪个开关是「决定性的」。

**建议**
合并为：**一个「答题模式」下拉（仅题库 / 仅AI / 先题库后AI / 不答题）**，删掉 `题库通道`、`LLM 通道` 两个开关（或保留为高级项折叠起来）。让用户只有一个心智入口。同时在下拉框正下方动态显示一行实时结论，例如「当前：先查题库，查不到问 AI（deepseek-chat）」。

### [UX-FR-16] 【严重】在非播放页初始化过一次后，脚本永远不会再自动启动
**证据**
- `src/07-main.js:10-14`：
  ```js
  let initialized = false;
  async function boot() {
    if (initialized) return;
    initialized = true;   // ← 进入即置真，失败也不回滚
    ...
  ```
- `src/07-main.js:26-31`：等 `video` 30 秒，等不到就 `Log.warn('30 秒内未找到视频元素，可能不在播放页')` 后 **return**（此时 `initialized` 已经是 `true`）
- `src/07-main.js:56-69` SPA 监听里唯一的补偿逻辑是 `if (!initialized && v) boot();`——**因为 `initialized` 恒为 true，这行永远不会执行**
- 结果：用户在课程列表页停留超过 30 秒后，再点进任意视频（SPA 路由，不刷新页面），`watchSpa` 只重新绑定 video（`07-main.js:59-65`），**永远不会调 `Scheduler.start()`**
- 用户能看到的唯一线索是 30 秒前那条 warn，而它 8 秒前就在日志里被埋掉了

**小白感知**

**建议**
1. `boot()` 在 `waitFor('video')` 失败时**回滚 `initialized = false`**，让 SPA 监听能补启动。这是一行代码的修复。
2. 30 秒找不到视频时给**常驻面板提示**：「还没检测到视频。如果你已经在播放页，点『启动』手动开始；如果不在，先点进一个视频小节。」
3. 把 `waitFor('video', 30000)` 的等待过程可视化：状态页显示「正在等待视频加载…（已等 N 秒）」，而不是干等。

按用户那句话「**开启自动就是全部自动，不需要点击交互任何按钮**」来验收当前 v0.2.1：

- **播放链路已达标**：`autoPlay / autoNext / skipFinished / mute / resume` 全部默认开（`00-config.js:14-23`），`07-main.js:48` 入口自动 `Scheduler.start()`，用户确实一个键都不用按。✅
- **答题链路不达标**：`autoAnswer: false`（`00-config.js:29`）+ 必须人工填 Key + 必须人工开 UI 开关；而且一旦打开却没配好 Key，会走到 `11-solver.js:82-88` 的**静默随机兜底**，属于「自动化假象」❌
- **异常链路不达标**：提示 8 秒消失（`06-panel.js:483`）、日志全是 debug 刷屏（`00-config.js:44` + `06-panel.js:462`）、关键分支从不弹面板提示（题库失败只在 `09-bank.js:136` 打 debug）❌
- **「非播放页先初始化」死区**（`07-main.js:10-14` + `:68`）会让相当比例的自然使用者遭遇「装了完全不动」，这是最需要在本轮修掉的一条。

### B.3 🚨 新增警报：`autoAnswer` 默认 true 把 UX-FR-3 升级为「开箱即中」

把 `autoAnswer` 改成默认 `true` 本身**正确且符合用户诉求**（「开启自动就是全部自动」）。但随机兜底没同步处理，于是形成了这样一条完整链路：

```
【默认配置，用户什么都不改】
00-config.js:29  autoAnswer: true      ← 新改的，弹题自动处理
00-config.js:31  bankUrl: localhost:8060 + bankEnabled: true   ← 绝大多数学生没跑本地题库
00-config.js:35  llmKey: ''            ← 空，LLM 分支被 11-solver.js:70 的前置条件整个跳过
        ↓
11-solver.js:83-88 随机选择一个选项，只打一条 Log.warn
        ↓
答案被真的点上去（13-answerer.js 的 flex.click()），写进平台答题记录
```

**后果**：一名完全按默认配置使用的学生，每一道课中弹题都会被**随机勾选，正确率约 25%**，而界面上没有任何常驻提示。这不再是「配置错了才会遇到」，而是**默认就会发生**。

**建议（二选一，建议第一个）**
1. 保留随机兜底，但**先体检再决定**：`13-answerer.js` 进入作答前调一次通道健康检查；若「题库 ping 失败 且 llmKey 为空」，则**不勾选任何选项**，改为弹出常驻提示：「未配置任何答题通道，已跳过本题（避免乱答）。去『设置』填 API Key，或关闭『题库通道』后启动本地题库。」宁可不答，也不要替用户蒙 —— 很多课程限制重答次数，乱答是不可逆伤害。
2. 或者在小结起见：至少把 `11-solver.js:87` 的 `Log.warn` 升级为 `panel.alert(..., 'error')` + 常驻，让用户在状态页能看见「当前答题方式：随机（未配置）」。

**顺带建议**：既然 `autoAnswer` 默认开了，`05-scheduler.js:189-200` 那条「未开启自动答题，直接关闭弹题继续播」的分支就从主路径降级成了边缘路径 —— 这是好的改进，但意味着**现在必须保证「答题」这条主路径绝对不能出错**，进一步支持上面的建议 1。

### B.4 🆕 新增发现：停止条件的总结文案会「撒谎」

新增的自动停止功能引入了新的文案不一致：

- `05-scheduler.js:53-56` / `:65-68` 按设定时长或节数达标时，调用 `_stopByCondition(title, detail)`
- `05-scheduler.js:79` 最终同样落到 `finishAll(title + '（' + detail + '）')`
- 而 `05-scheduler.js:403` 是硬编码：`ZHS.Log.info('=== 全部课程已看完 ===')`

于是**用户设定「看 30 分钟后自动停」**，达标时：
- 日志打印：`=== 全部课程已看完 ===`（假的，实际是到点了）
- 总结卡标题（由 `06-panel.js` 的 `allDone` 判定，此时为 false）：「运行已结束（仍有未完成课程）」（也不准确，用户是主动设定到点停止）
- 用户真实意图：到点了，正常结束

三处说法互相矛盾。**建议**：`finishAll` 的日志与标题都改成接收 `reason`，如「=== 运行结束：<reason> ===」；总结卡标题按 reason 分类展示（达标停止 / 全部看完 / 仍剩未完成）。

这是新功能带来的一处小文案债，成本极低，建议顺手一起改掉。
